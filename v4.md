# JobAgent 4.0: autopilot

Written 2026-11-25. v4 is **v3 in full** (`v3.md`: its rules, engine, screening, polish and migration) **plus autopilot**: after one setup,
JobAgent finds jobs, prepares them and sends the strong ones by itself. It asks the user only for what only they can give,
and ongoing upkeep takes one tap at most. Where this file and `v3.md` disagree, this file wins.

## 1. What v2 already does unattended (reuse it, don't rebuild it)

- Auto-apply with a cancellable countdown (`review.autoGate`, `startAuto`), company cooldown, restart recovery (`planRecovery`).
- Auto-search on a timer with a Claude reserve, quiet hours, a weekly summary, a related-titles learner.
- Background mode (Task Scheduler at logon, restarts after a crash), a health check every 6 h, self-repair behind an approval.
- An answer pack in setup (work authorization, sponsorship, start date, relocation, EEO), saved answers reused by meaning.
- Saved LinkedIn/Indeed passwords for re-login. A daily update check (it only tells the user).

## 2. What still needs a person in v2, and the v4 fix

| Gap (measured on the v2 install, `v3.md` §2) | v4 fix |
|---|---|
| Each job is a full Claude session: 1.6 five-hour windows bought 5 reviews, so the limit, not the user, caps throughput | v3 engine E1–E6 |
| 31 of 37 analysed jobs could have been dropped by code (wrong country, pay, kind of work) | v3 screening S1–S6 |
| The most common sensitive question with no saved answer is the salary expectation | AP4: asked once in setup |
| Waiting questions and reviews from auto-search pile up | AP6: expire after 7 days, auto-search jobs only |
| No limit on how much goes out while nobody watches | AP3: daily cap, circuit breaker, plus v3 P3 (first 3 real sends per form type wait) |
| Each search, prepared job and auto-apply sends its own message | AP8: autopilot sends one daily digest; only "needs you" rings |
| Updating needs a terminal | AP7: one-tap update from Health |
| Job folders grow forever (screenshots, PDFs, postings) | AP6: prune |
| Turning autonomy on means finding 5 settings | AP1: one Autopilot choice at the end of setup and in Settings |

Not changed: generic (non-Greenhouse/Lever/Ashby) forms, unusual fields and drafted private answers still always wait for
the user (`autoGate`). That is the safety line, not a gap.

## 3. Rules

`v3.md` §1.3 rules 1–10 all stand. v4 adds:

11. **Autopilot sends only through the existing gate.** `review.autoGate` → `approve(id, 'auto')` → the submit queue. No new path
    writes `approval.json` or calls `jobagent submit`.
12. **Unattended sending is bounded.** At most `apply.daily_max` real submissions a day. After 2 real submissions in a row that end
    `NEEDS_HUMAN` or `FAILED`, auto-apply holds itself until the user taps Resume.
13. **Autopilot never turns practice mode off.** Going live stays the Settings button with its confirm (rule 2).
14. **Deleting is limited to what can be rebuilt or is no longer needed.** The prune never touches `SUBMITTED`/`APPLIED_SELF` jobs, receipts,
    `approval.json`, the profile, resumes or settings.

## 4. v4 work packages

**AP1 · Autopilot in one choice `S`.** Setup's last step and Settings → How I apply offer "🤖 Autopilot": auto-search on,
`apply.mode: auto`, `notify.digest: daily`, auto-apply messages silent. "I review each one" keeps v2's behaviour. Practice mode is untouched.
*Done when:* a ui test covers both choices and `fits()`; choosing Autopilot writes exactly those settings.

**AP3 · Daily cap and circuit breaker `S`.** `apply.daily_max` (default 10). `autoGate` refuses past the cap ("today's 10 are sent; the rest
go tomorrow") and while `data/autopilot.json` has `hold`. `onResult` sets `hold` after 2 consecutive real failures and sends one loud
message with ▶ Resume. *Done when:* unit tests of `autoGate` for the cap and the hold, and a flow test where two failures set the hold.

**AP4 · Salary expectation in setup `S`.** After the minimum salary step: "When a form asks your expected salary, what should I say?"
(my minimum / a number I type / leave it for me to ask). Saved as the sensitive answer `salary_expectation`. *Done when:* a ui test.

**AP6 · Daily upkeep `S/M`.** `jobagent maintain` (app-only, denied to Claude) run once a day:
- prune: for jobs in `SKIPPED`, `CLOSED`, `FAILED`, `DRY_RUN_DONE` and older than 30 days, delete `posting.md`, `screenshots/`, `*.pdf`, `*.docx`, `*.png` and the listing; keep the JSON;
- expire: `discovery` jobs waiting in `NEEDS_ANSWERS` or `AWAITING_APPROVAL` for 7 days go to `SKIPPED` ("No answer in a week; tap Look again to bring it back");
- trim `screened.jsonl` to 30 days.
It returns counts; the daily digest mentions them. *Done when:* pytest on a fixture data folder shows exactly what goes and what stays.

**AP7 · One-tap update `S`.** When the daily check finds commits, Health shows "⬆️ Update and restart". It writes `data/update.json` and exits
with code 75. `start.ps1`/`start.sh` loop: on 75, `git pull --ff-only`, `bun install`, `uv sync`, then start again; on a failed pull they start
the old version and the app says so. *Done when:* the start scripts handle 75, and a test covers the button.

**AP8 · Daily digest `S`.** Once a day after quiet hours, one silent message: sent (names), waiting for you (reviews, questions, kits),
filtered out (count, top reason), upkeep counts, and the Claude limit used. With `notify.digest: daily`, the per-search digest is not
sent. *Done when:* a pure `dailyPage` with a ui test and `fits()`.

**AP5 · Emailed security codes, opt-in (optional; ask the maintainer first) `M`.** Read the Greenhouse code from the user's inbox over
IMAP (`imaplib`, app password in `keyring`), code only by regex, never shown to Claude. Off by default.
